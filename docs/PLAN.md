# AIRLOCK：个人项目设计与执行方案

## 定位

AIRLOCK 是面向 Agent 写操作的审批与受限执行实验室。当前只保护固定 SQLite 合成业务表，不是任意工具透明代理，更不是生产安全认证产品。

适合简历与面试的主线是：**人批准的对象，必须与服务端最终执行的参数、策略和数据快照一致。** 工程难点在授权边界、TOCTOU、幂等、崩溃一致性、可理解的影响证据和可信验收，不在确认按钮本身。

这是个人项目，允许 AI 辅助编码，但不能虚构团队、工作经历、独立手写贡献或生产用户。是否能写入简历取决于本人是否跑过演示并能解释核心路径。

## 对原始设想的修正

- HITL 已有成熟实现，“所有开源只有放行与阻断”不成立。把创新表述为工程组合和场景聚焦，不争首创。
- “可逆”不等于“获准”，低影响也不等于有业务权限。所有支持写入，包括零变化写入，都需要 reviewer。
- 精确预演只在固定模式、白名单操作/函数和同一快照内成立。不能把 SQLite 回滚当作任意 SQL、Shell 或网络操作沙箱。
- 无验证备份就标为未知；当前没有提交后自动撤销。预演不可用时阻断，不让 LLM 猜数字然后放行。
- 持久化 pending + 状态查询把审批寿命与连接寿命分离。选择这种设计不能被写成“MCP 不支持长任务”。
- 3 秒决策、人类正确率与疲劳下降是待检验假设。<1 秒批准是观察信号，不能单独证明敷衍审批。
- 1206 行是合成演示种子。没有重建完整事故证据链，不宣传精确复原 Replit 事故或推断其因果。

## 本版流程

```text
Agent / MCP host：只有 agent token
  -> HTTP 接入 -> Gate 核心
      -> 合法有界只读：pass，执行并审计
      -> 不支持/越界/预演失败：block
      -> 支持写入：need_approval，持久化 pending 与影响快照
           -> 独立 reviewer 审批台：数量、diff、参数、恢复限制
           -> 写事务内再次验证 TTL、版本、参数、策略与数据指纹
           -> 业务效果 + 终态 + 审计，同库原子提交
```

## 阶段门禁

| 阶段 | 交付 | 门禁 |
|---|---|---|
| 设计 | 范围、威胁模型、接口与状态 | 不把竞品猜测或计划当事实 |
| 核心 | 策略、受限预演、审批、幂等、审计 | 无批准不写；漂移失效；异常和进程退出回滚 |
| 产品 | 中文审批台、字段 diff、SSE、历史 | 真 API/真数据变化，凭据不在 URL/持久存储 |
| 接入 | stdio MCP、官方 SDK 互通、脚本 Agent | pending 不是执行成功；无审批工具 |
| 验证 | 测试、合成回归、原生浏览器、Docker | 验证子进程退出码和实际产物，不只看 CI 图标 |
| 交接 | 证据、面试文档、Codex 清单、记忆分支 | 每项区分 PASS、FAIL、NOT RUN、环境受限 |

## 原能力范围对照

C1：HTTP + 最小 stdio MCP，非任意上游透明代理。C2：确定性规则和 SQLite authorizer，未实现 CEL/YAML。C3：受支持快照精确差异。C4：事务提交前回滚，无提交后恢复。C5：未实现 LLM 语义评分。C6：持久化等待、TTL、固定独立审批身份；无多人路由。C7：影响优先界面已实现，体验提升需真人实验。C8：只读免审批、请求幂等和队列限额；无批量写批准、学习降级。C9：结构化拒绝和模拟器 SELECT 替代。C10：原始快照与可校验 HMAC 审计，无外部锚定。C11：合成回归与独立测试。C12：状态与内部评估延迟，无分布式 tracing 或真实 token 成本。

## 下一版优先级

先由 Codex 独立复核当前门禁，再用操作者授权的真实模型/host 验证；随后安排有真实任务授权金标的真人实验。再考虑 Vue 重构、多人路由或一个生产数据库适配器。不要为了技术关键词先加 Redis、LangGraph、RAG 或 CEL；远程副作用需要重新设计结果未知、幂等收据和恢复机制。

出现未授权写、绑定替换或提交不一致立即返工；预演难以说明则收窄支持范围；人理解错误则改信息设计，不以更快点击作为唯一成功。
