# 面试讲解：只说实现和证据支持的内容

## 一分钟介绍

我做的是 Agent 数据操作的变更审批工作台。不是让模型保证安全，而是把执行权放到服务端。Agent 只能提出结构化工具请求，后端在 SQLite 一致性影子快照上计算包含级联影响的差异；人独立登录批准后，服务端复核授权与策略，执行器在事务里核对参数和数据快照。变化让旧计划失效。业务修改和回执同事务提交，用于重试和进程崩溃后的核实。Vue 展示 diff 和审计，MCP 用官方 SDK 实际往返。范围仅限受控 SQLite，不是假称所有工具都能安全预演。

## 与普通确认弹窗有什么不同？

按钮只表达一个意愿。系统还要核对批准者身份、批准的具体内容、执行时目标是否变化，以及响应丢失后究竟是否执行。对应 auth.py、plans.py、service.py、target.py。人工审批不是本项目首创，差异在证据与事务机制的完整连接。

## 为什么不用 MySQL、Redis 和 RAG？

预检与执行使用相同数据库引擎，SQLite 便于个人复现。持久 jobs 支持单工作者恢复，不先引入队列。固定策略不需要检索增强。代价是单写者、有限容量、全表状态冲突；本项目不宣称高并发企业架构。

## 预检为什么不能只看 rowcount？

删除客户可能级联删除备注。执行器比较全部受管表的主键级前后记录，直接变化与级联分别统计。独立 Python oracle 不调用生产 diff 函数，用来检查实际输出；预检前后真实目标保持不变。精确只针对支持的 Schema 与当前快照。

## 批准之后数据变了怎么办？

等待人不锁目标。执行器在 BEGIN IMMEDIATE 中读取和核对 Schema、全受管业务状态，执行原请求后再次核对实际差异。内容变化就 STALE，重新生成计划。本版无关行变化也失效，是保守取舍。授权与风险策略在网关领取前检查，不把两个数据库说成一个分布式事务。

## 响应丢失会不会多改一次？

目标事务把业务修改和 operation_id 唯一的回执一起提交。相同计划重试返回原回执，换计划则冲突。元数据库尚未记成功可以用回执恢复。真实测试在目标提交后 os._exit(73)，恢复仍只修改一次版本。范围是受控目标的事务内幂等效果，不是所有分布式系统 exactly-once。

## 模型说已经获得批准怎么办？

模型没有审批凭据与执行器秘密。严格契约也不接受 approved 或 role。实际审批来自独立人类会话并绑定计划/视图/版本；模型解释不能覆盖服务端事实。模型客户端实现检查点恢复，但未提供远端 API 凭据，因此不能说本次已验证真实模型推理。MCP 接入则已用官方 SDK 真进程测试。

## 断线和重复点击如何处理？

SSE 只是通知，权威状态在数据库。重连使用事件 ID，轮询补偿。审批使用预期版本和幂等键，并发批准/拒绝只有一个胜者。任务领取前允许取消，之后不能承诺取消成功。前端对旧请求响应做版本/会话检查，不让迟到响应覆盖新状态。

## 怎样证明 Agent 绕不过去？

不只在提示词里约束。Compose 中 Agent 无目标卷、元数据库卷、审批秘密或执行器网络，只能访问网关。脚本会验证这些边界。普通本地同账号进程不具备同等隔离，宿主机管理员失陷也不在保证范围。只能说明已测试威胁模型内的限制，不能声称绝对安全。

## 如何说明 AI 辅助开发中的个人贡献？

如实说明使用 AI 实现辅助。应能独立解释范围、信任边界、计划绑定、短事务与回执恢复，复现失败测试，找到对应代码并修改。不要假称所有代码手写；也不要只背 README。真实发现、修复和复测证据比编造性能和用户实验更重要。
